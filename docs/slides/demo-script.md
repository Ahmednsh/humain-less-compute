# Demo video script (≤ 3 minutes)

Platform rule: the video shows the solution working; it does not repeat the slides. Record the terminal and the HTML report. Narration language: participant's choice (Arabic or English); on-screen text is English.

**Before recording:** have `results/report.html` from the final runs open in a browser tab; terminal font large; `.env` present. The demo set is `data/demo.jsonl`: 8 tasks ordered easy → hard (three tier-1 lookups, three tier-2 money aggregates of which one is in Arabic, two tier-3 rankings incl. year-over-year growth). Dry run on 31 Oct: 8/8 correct, $0.03, 10 s; routes small/small/small/small+verify/small+verify/small+verify/large/large. Add `--concurrency 1` when recording so the lines appear one at a time in that order. No escalation fires on this set (none fired in any of the 390 final-config P3 tasks either), so the narration does not promise one.

| time | on screen | say |
|---|---|---|
| 0:00–0:20 | Title card: *Deliver AI with Less Compute — a budget-aware controller for ask-your-data analytics*. Then the 12-table schema diagram (from the slides). | Companies send every question to their biggest model with the whole schema and the whole history. Most of that compute is wasted. This controller decides, per question, which model to use, which tables to send, and when a second opinion is worth paying for. |
| 0:20–1:40 | Terminal: `npm run cli -- eval --policy P3 --tasks data/demo.jsonl --db data/company.sqlite --limit 8 --concurrency 1`. Point at the live lines: `route=small tables=1`, `tables=2`, then `ver=1` on the revenue questions (one of them Arabic), then `route=large tables=5` on the growth question. | Watch the decisions. A price lookup goes to the small model with one table instead of twelve, for three hundredths of a cent. A revenue total is a money number, so the small model's answer gets a large-model second opinion before it is trusted; the Arabic question takes the same path with no special handling. A year-over-year growth question scores high on the router and goes straight to the large model with the five tables it needs. If a cheap answer ever fails its free checks or the verifier rejects it, the controller escalates once and the failed attempt stays in the bill; on this set nothing needed it. Every line is a logged JSON row with tokens, cost and latency. |
| 1:40–2:30 | Browser: `results/report.html`. Hover the rows P0 → P1 → P2 → P3; then the robustness table. | Same 150 questions, six policies. The baseline is the large model always. Adding the router, then pruning, then selective verification, each row cuts cost per successful task while accuracy stays inside the two-point floor and p95 latency inside 1.25× the baseline. Verify-always shows blanket verification is not worth it. On a renamed schema, Arabic questions, and a swapped small model, the controller adapts: escalation rises, accuracy holds. |
| 2:30–2:50 | Report: the held-out section. | The final numbers come from a held-out set generated with a secret seed outside the repository, including six question types never seen during development, run once. |
| 2:50–3:00 | README limitations. | Synthetic data, one domain, a lexical router, two days. Everything is reproducible with one command. Thank you. |

Cut anything that runs long; the ablation table and the held-out line are the two things that must be on screen.
